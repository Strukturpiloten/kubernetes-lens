# Kubernetes extension resources

KubernetesLens admits stable and historical beta custom-resource-definition (CRD), mutating webhook configuration, and validating webhook configuration roots. The codecs preserve API versions, explicit presence, and unknown-field evidence. Beta admission APIs and beta CRDs are available only for Kubernetes 1.20–1.21; stable roots are available from 1.20. Stable webhook `matchConditions` retain their 1.27 field boundary and feature-gate evidence. CEL expressions are retained but never evaluated.

CRD schemas use bounded flat arenas. Stable and beta root types remain distinct, schema views borrow selected fields and preserve `Presence`, and recursive references stay inside the owning schema arena. Beta views expose beta-family enum/example, union, dependency and external-documentation helpers. Their protected payloads and `Presence` remain intact; borrowed views perform no conversion or allocation. Stable and beta child handles remain arena- and family-checked. Protected enum and example JSON remains redacted in debug output and requires explicit source access to serialize. The local checker covers a documented subset only; structural Kubernetes semantics, CEL, defaulting, pruning, and conversion remain unsupported. It does not claim API-server validation or admission.

`AuthoredResource::custom_object` accepts a protected complete object plus an expected API version and kind. `ResourceSet::from_authored` checks that identity under cumulative construction limits, records `NativeAuthored` evidence, and emits a deterministic native snapshot. The body remains opaque: generation requires explicit protected-output and opaque-field policies and does not confer typed custom-resource or controller support.

`ResourceSet::check_custom_documents` checks explicitly supplied custom resources against explicitly supplied CRDs, using the full target profile and caller-lowered processing ceilings. Its source-bound results retain resource identity and protected body, immutable evidence, source/List coordinates, selected CRD/version/schema pointers, and local supported-subset outcomes. Missing, ambiguous, mismatched, unserved, unsupported, schema-violation, incomplete, and limit-exceeded results remain distinct. Source pointers and private bytes require explicit access to reveal. Unsupported occurrences carry the exact keyword pointer, including distinct private unknown keys and List prefixes; default diagnostics remain redacted. Exhausting the cumulative check budget returns a terminal `Err`, so a successful result vector always covers every supplied custom document.

Target-specific reference graphs retain a status record for each supplied custom document. Only a unique CRD binding whose selected version is served, whose scope and schema are present, and whose supported local schema check completes without violations produces a positive CRD dependency. The edge resolves to the actual supplied CRD `ResourceId`; its sealed `SuppliedCustomResourceDescriptor` identifies the selected nested version and schema by source pointer. Missing, ambiguous, invalid, unserved, unsupported, schema-violation, incomplete, and target-profile-required results do not produce that edge. A sealed descriptor belongs to the exact supplying resource set and full target profile. Each graph pass rechecks the current supplied documents and compares the effective CRD body, selected binding and target under the inherited budget. Descriptors from other sets (including reused SourceIds), stale CRD edits, or different/incomplete targets cannot authorize an edge. A graph without an explicit target records `TargetProfileRequired` when a source-selected schema cannot be checked.

Each recognized custom document also produces an external, unverified operator prerequisite. This records that controller reconciliation is needed; it does not identify or understand a controller, or establish installation, reconciliation, availability, or runtime conformance. These checks and relationships use the graph operation's shared processing session and source/List coordinates.

Typed CRDs establish descriptors from their group, kind, scope, served/storage versions, and schemas. They do not bind arbitrary resources unless the caller runs the offline checker. No code invokes conversion or validation webhooks, discovers resources, contacts a cluster or controller, infers Secrets or certificates, or claims operator reconciliation, availability, backup, restore, or provisioning behavior. Generic custom-resource support does not replace typed implementation of admitted built-in kinds or an operator-specific adapter.

Webhook validation is limited to explicit local scalar checks. Stable-v1 Create checks permit only `None` and `NoneOnDryRun` side effects. Existing stable resources may retain `Some` or `Unknown` from beta creation; unspecified validation intent preserves these values with a `NativeContextRequired` warning. Historical beta APIs retain all four values within their served version range. A service client configuration, including an explicitly selected CRD conversion webhook, may produce a supplied-resource prerequisite when a service name is present; absent namespace remains unknown. A non-null URL creates an external remote prerequisite even when `service` is explicitly null. URLs and CA bundles remain protected output paths. The implementation performs no callback, network lookup, TLS validation, Secret inference, or certificate decoding.

Focused local regressions run with `cargo test --locked --test extensions --test extensions_final_corrections` and `cargo test --locked --lib resources::extensions`. These check the offline contract only; official-fixture acceptance, API-server and controller conformance are tracked separately.
